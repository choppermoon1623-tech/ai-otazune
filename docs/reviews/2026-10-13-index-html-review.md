## 1. 概要

`index.html`（全1533行）を対象に、生徒側UI・先生側UI・Firestore連携・セキュリティルールとの整合性・状態管理・エラーハンドリング・アクセシビリティの観点から静的コードレビューを実施しました。

教育現場における運用の工夫（入力項目の構造化、AIへの丸投げ防止、コピー方式を既定とした安全設計、丁寧なエラー表示）が随所にみられる堅牢な設計となっています。
一方で、外部連携（逆引きシステムとの相乗り）におけるデータ消失リスク、Firestoreルールとクライアント側バリデーションの齟齬による誤認メッセージの発生、二重送信制御の漏れなど、改修を推奨する点がいくつか確認されました。

## 3. 詳細指摘

### 指摘 1: 【重要度：高】受付編集時に「計測・制御（keisoku）」型が脱落する問題

- **対象箇所**:
  - `index.html` 1368〜1376行（`openRoomModal`）
  - `index.html` 1385〜1395行（`rSave.onclick`）
- **事実（確認したコード）**:
  - `HANDOVER.md` 5-b項に「計測・制御 逆引きシステム（`keisoku-gyakubiki`）が同じコレクションに相乗りし、`kind:"keisoku"` で届く。`KINDS.keisoku` を消してはいけない。`KIND_ORDER` に入れないのは意図的で、この画面のフォームからは出させない」と規定されています。
  - 受付編集モーダル（`openRoomModal`）では、チェックボックスの生成対象を `KIND_ORDER`（`shirabe`, `sakubun`, `idea`, `free`）のみに限定しています。
  - 保存時（`rSave.onclick` 1385行）では、画面上のチェックされたチェックボックスの値のみを配列 `kinds` として取得し、Firestore に保存しています。
- **影響**:
  - 逆引きシステム専用または共用の受付（`kinds` に `"keisoku"` が含まれる受付）を先生が「✎（受付の設定）」で開いてそのまま「保存」した場合、`"keisoku"` が配列から消去されます。
  - その結果、逆引きシステム側からの受付連携が阻害されたり、生徒側の案内表示（871〜877行）が意図しない挙動になる可能性があります。
- **修正案**:
  - `EDIT_ROOM` を編集する際、既存の `EDIT_ROOM.kinds` に含まれる `KIND_ORDER` 外の型（例: `"keisoku"`）を保持してマージ保存する実装に変更します。
  ```javascript
  const extraKinds = (EDIT_ROOM && EDIT_ROOM.kinds)
    ? EDIT_ROOM.kinds.filter(k => KIND_ORDER.indexOf(k) < 0)
    : [];
  const kinds = [
    ...Array.prototype.slice.call($("rKinds").querySelectorAll("input:checked")).map(x=> x.value),
    ...extraKinds
  ];
  ```

### 指摘 2: 【重要度：高】氏名文字数超過による `permission-denied` と誤った案内文

- **対象箇所**:
  - `index.html` 906行（名前入力欄描画）
  - `index.html` 941〜950行（送信前バリデーション）
  - `index.html` 967〜969行（エラーハンドリング）
  - 関連: `firestore.rules` 64〜65行
- **事実（確認したコード）**:
  - `firestore.rules` 64〜65行では `request.resource.data.name is string && request.resource.data.name.size() <= 40;` と厳格に文字数が制限されています。
  - クライアント側（`index.html` 906行）には `maxlength` 属性がなく、送信時（941行）にも `name.length <= 40` のチェックがありません（各フィールドの4000字チェックのみ存在）。
  - もし生徒が40文字を超える名前を入力して送信した場合、Firestoreルールにより拒否され `e.code === "permission-denied"` となります。
  - クライアントのエラー処理（967〜968行）では：
    ```javascript
    if(e && e.code === "permission-denied"){
      toast("いま受付が閉じているようです。先生に聞いてください。");
    }
    ```
    となっており、ルール違反の全般を「受付が閉じている」と判断してトースト表示します。
- **影響**:
  - 受付が開いているにもかかわらず、生徒の画面には「いま受付が閉じているようです」と表示され、生徒も先生も原因（文字数オーバー）を特定できず混乱します。
- **修正案**:
  1. 名前入力欄（906行）に `maxlength="40"` を追加する。
  2. 送信ボタン押下時（941行付近）に `if(name.length > 40) { toast("名前は40文字以内で入力してください。"); return; }` のチェックを追加する。
  3. 出席番号欄（902行）にも `maxlength="10"` 程度の適切な制限を設ける。

### 指摘 3: 【重要度：中】「番号のみ」受付で送信すると保存済み氏名が空文字に上書きされる問題

- **対象箇所**:
  - `index.html` 938行, 952行
- **事実（確認したコード）**:
  - 名前モードが「出席番号だけ書かせる（`mode === "no"`）」の場合、`renderSFields` (903行) では名前欄（`sName`）が描画されません。
  - 送信処理（938行）では `const name = $("sName") ? $("sName").value.trim() : "";` となり、`name` は `""` になります。
  - 送信完了前（952行）で `STU.no = no; STU.name = name; lsSet(LS_STU, STU);` が実行され、ローカルストレージの `STU.name` が `""` に上書きされます。
- **影響**:
  - 他の授業で一度名前を入力・保存していた生徒が、「番号のみ」の受付で一度でも送信を行うと、端末に保存されていた名前が消去されます。次回「名前必須」の受付を利用する際に名前の再入力が必要となります。
- **修正案**:
  - DOM上に `sName` 入力欄が存在する場合のみ、`STU.name` を更新するようにガードします。
  ```javascript
  STU.no = no;
  if($("sName")) STU.name = name;
  lsSet(LS_STU, STU);
  ```

### 指摘 4: 【重要度：中】参加ボタンや先生対応ボタンの `disabled` 制御漏れ

- **対象箇所**:
  - 生徒画面: `index.html` 798〜803行（`sJoinBtn.onclick`）
  - 先生画面: `index.html` 1232〜1265行（`mReturn`, `mWork`, `mReject`, `mDelete`）
- **事実（確認したコード）**:
  - おたずね送信（`sSend` 954行）や受付作成（`rSave` 1388行）ではボタンの非活性化（`btn.disabled = true`）が行われています。
  - しかし、受付に入るボタン（`sJoinBtn`）は非同期関数 `joinRoom` の完了を待たずに複数回クリック可能です。
  - 先生モーダルの各操作ボタン（「生徒に返す」「対応中にする」「見送りにする」「削除」）も、非同期通信中（`saveCur` や `deleteReq`）にボタンが無効化されません。
- **影響**:
  - 通信が遅い環境やタブレットでの連打時に、`watchRoom` や `watchReqs` の多重初期化競合が発生したり、Firestoreへの重複更新・重複削除リクエストが送信される可能性があります。
- **修正案**:
  - 処理開始時にボタンを `disabled = true` に設定し、`finally` またはモーダル閉鎖時に解除する統一的な処理を追加します。

### 指摘 5: 【重要度：中】受付削除時におけるサブコレクション直列削除の処理中断リスク

- **対象箇所**:
  - `index.html` 1415〜1428行（`rDelete.onclick`）
- **事実（確認したコード）**:
  - 受付削除時、Firestoreの仕様（親ドキュメントを削除してもサブコレクションは削除されない）に対応するため、`for(const r of TREQS.slice()) await fbq.deleteReq(id, r.id);` によって1件ずつ直列で削除しています。
- **影響**:
  - おたずね件数が多数ある場合、直列処理による通信遅延で数秒〜十数秒以上待たされることになります。
  - その途中で通信エラーやブラウザの離脱が発生すると、一部のおたずねだけが削除され、親の受付が残る（または親の削除前に処理が中断する）中途半端な状態になります。
- **修正案**:
  - 短期的には削除処理中の進捗表示（ボタンの非活性化と「削除中...」の表示）を行い、途中で画面を閉じないよう促す。
  - 中長期的には `writeBatch` を用いた一括バッチ削除への移行を推奨します。

### 指摘 6: 【重要度：低】未定義の `mode === "none"` 判定コードの残存

- **対象箇所**:
  - `index.html` 386〜390行（HTML）
  - `index.html` 898行, 940行（JavaScript）
- **事実（確認したコード）**:
  - `<select id="rName">` に定義されている選択肢の値は `"req"`, `"no"`, `"opt"` の3種のみです。
  - 一方で JavaScript 側には `if(mode !== "none")` や `if(mode !== "opt" && mode !== "none" && !no)` といった判定が存在します。
- **影響**:
  - 現状の動作には影響しませんが（条件式は常に真として評価される）、将来コードを読む開発者が「`none` というモードが存在するのか」と誤解する原因になります。
- **修正案**:
  - 「出席番号も名前も完全に不要」というモードを追加する予定がなければ、不要な `mode !== "none"` の分岐記述を整理することを推奨します。

### 指摘 7: 【重要度：低】外部CDN（cdnjs）依存による学校NWでのQRコード描画失敗リスク

- **対象箇所**:
  - `index.html` 553行
  - `index.html` 1464〜1480行（`drawQr`）
- **事実（確認したコード）**:
  - QRコード生成用スクリプトとして `https://cdnjs.cloudflare.com/ajax/libs/qrcode-generator/1.4.4/qrcode.min.js` を外部CDNから読み込んでいます。
  - スクリプトが読み込めなかった場合（`typeof qrcode !== "function"`）のフォールバック表示（1466行）は既に実装されています。
- **影響**:
  - 自治体や学校のセキュリティポリシー（フィルタリング）によって外部CDNドメインへのアクセスが遮断された場合、教室のプロジェクター等でQRコードを表示できなくなります。
- **修正案**:
  - 当該JSライブラリをプロジェクト内の静的アセット（例: `assets/js/qrcode.min.js`）として配置し、相対パスで読み込む方式に変更することで、外部通信制限下でも確実に動作するようになります。
